## Prognosify DB — adversarial review (single-tenant, intra-hospital)

**I did not execute any SQL.** There is no PostgreSQL, `psql`, or Docker in this environment. Every exploit below is derived by static reading of the four migrations; each is labelled CONFIRMED (the policy/grant/trigger text alone decides it) or THEORETICAL (depends on runtime behaviour I could not observe).

Files read in full: `migrations/000_extensions.sql`, `010_tenancy_identity.sql`, `020_clinical.sql`, `030_documents_ai.sql`, `040_admin_billing_audit.sql`, `README.md` — all under `C:\ALL FILES\Deepak Files\Project\New folder-p\prognosify-db\`.

Two runtime assumptions the analysis rests on, stated because they cut both ways:
1. RLS applies to tables referenced inside another policy's subquery (this is what makes `ai_risk_factor_select` and `app_user_select` safe, and it is the only thing making them safe).
2. A dotted custom GUC in an unreserved class (`app.allow_clinical_rewrite`) is settable by any role, including `authenticated`. This is what breaks the append-only guards.

## PART A — Attacker holds a PATIENT login at Hospital A

### A0. No direct read path to another patient exists. CONFIRMED negative.

I enumerated every table a seat with `roles = {patient}` can `SELECT`. Every clinical table either excludes the patient entirely (`app.is_clinician()` on `lab_order`, `clinical_note`, `document_text`, `ai_risk_score`, `ai_citation`, `ai_risk_factor` via parent, `document_text_chunk`, `lab_panel` via `is_staff()`) or pins the row to `patient_id = app.current_patient_id()` (`patient_condition`, `patient_allergy`, `encounter`, `vital_sign`, `medication_order`, `appointment`, `invoice`, `invoice_line`, `payment`, `care_team_member`, `audit.event`). `lab_result` additionally requires `released_to_patient_at IS NOT NULL`; `ai_finding` additionally requires `patient_visible AND review_state IN ('accepted','amended')`. All five views in 020 and all three in 040 carry `security_invoker = true`, and 020 §90.4 asserts it at migration time. No unfiltered `COUNT` surface is reachable: `organization_usage_daily_select` (040:1844) requires `hospital_admin` or `super_admin`, and `appointment_select` gives a patient only their own rows, so clinic-load inference is closed too.

The cross-patient read I did find (B1) requires a receptionist or clinician write first. A patient acting alone cannot reach it.

### A1. `public.patient` has no column guard — the identity-mapping column is patient-writable. CONFIRMED. HIGH.

`010_tenancy_identity.sql:1406-1412`:

```sql
CREATE POLICY patient_update ON public.patient FOR UPDATE
  USING (
    organization_id = app.current_org_id()
    AND (app.is_front_desk() OR app.is_clinician() OR id = app.current_patient_id())
  )
  WITH CHECK (organization_id = app.current_org_id());
```

`010:705-710` attaches only `t_touch` (BEFORE UPDATE) and `t_no_delete` (BEFORE DELETE). There is no `app.enforce_patient_writable_columns` on this table — `020:942` and `020:1588` attach it to `appointment` and `medication_order` and nowhere else. `010:1443-1444` grants `UPDATE ON public.patient TO authenticated`.

So the `WITH CHECK` re-verifies the tenant and nothing else, and every column of the caller's own chart is writable, including `portal_member_id` — the column that decides *which chart am I*:

```sql
-- as patient@gmail.com (Priya, MRN 108-921)
UPDATE public.patient SET mrn = '104-882' WHERE id = app.current_patient_id();
-- succeeds (unique per org, and Rosa's 104-882 is a different row only if unclaimed)

UPDATE public.patient
   SET status = 'merged', merged_into_patient_id = <any patient id in St. Luke's>
 WHERE id = app.current_patient_id();
-- succeeds; patient_merge_ck is satisfied. app.current_patient_id() (010:984-996)
-- excludes p.status = 'merged', so the attacker now resolves to NULL and every
-- patient-branch policy denies. Self-inflicted, but it also strands her clinical
-- rows: README states "Nothing follows the chain today."

UPDATE public.patient SET portal_member_id = NULL WHERE id = app.current_patient_id();
-- succeeds; releases the seat from the unique index patient_portal_member_uk,
-- which is the precondition for the receptionist attack in B1.
```

**Result:** a patient can rewrite their own MRN, demographics, DOB and merge state, and can detach their own portal link. Direct escalation to another chart is blocked only because `patient_update`'s `USING` pins the OLD row to `id = app.current_patient_id()` — the `WITH CHECK` would not have stopped it.

**Fix.** Add a column guard mirroring `app.document_before_update()` (`030:838-849`), freezing `portal_member_id`, `organization_id`, `mrn`, `status`, `merged_into_patient_id` against any caller who is not `hospital_admin`/`service_role`, and move portal linking and merge into RPCs. Tighten the `WITH CHECK` to repeat the `USING` predicate.

### A2. Direct answer to your item 2: `organization_member` is write-tight; `patient` is not.

`organization_member_write` (`010:1362-1366`) is `FOR INSERT ... WITH CHECK (hospital_admin OR super_admin)` — a patient cannot mint a seat. `organization_member_update` (`010:1368-1379`) carries a `WITH CHECK` identical to its `USING`, and `app.sync_member_identity()` (`010:530-546`) raises on any self-edit of `roles` or `status` (keyed on `OLD.auth_user_id = app.current_auth_uid()`, so a two-hospital locum is covered) and on any move of `organization_id`/`app_user_id`. `app.guard_app_user_update()` (`010:573-576`) makes `auth_user_id` immutable to everyone through the API. `platform_admin` has a SELECT policy and no write policy at all (`010:1384-1387`).

**Verdict: a patient cannot link themselves to a second patient record or grant themselves a staff role.** CONFIRMED negative.

The membership/mapping table that is *not* write-tight is `public.patient` (A1) and `care_team_member` (C4) — both have a `WITH CHECK` that only re-checks the tenant.

### A3. Patient can forge staff attribution on their own document. CONFIRMED. MEDIUM.

`030:1590-1601`:

```sql
CREATE POLICY document_update ON public.document FOR UPDATE
  USING (
    organization_id = app.current_org_id()
    AND ( (app.is_clinician() AND patient_id = ANY (app.care_patient_ids()))
          OR uploaded_by_member_id = app.current_member_id() )
  )
  WITH CHECK (organization_id = app.current_org_id());
```

`app.document_before_update()` (`030:825-896`) freezes the stored object, `patient_id`, `source` and `scan_status`, and blocks reclassification to `radiology_image`/NULL. It does **not** guard `doc_type_confirmed_by_member_id`, `doc_type_confirmed_at`, `retracted_by_member_id`, `patient_visible` or `file_name`, and no `enforce_patient_writable_columns` is attached to `document`.

```sql
-- patient uploads via the portal (document_insert permits source='patient_upload')
UPDATE public.document
   SET doc_type = 'other',
       doc_type_source = 'human',
       doc_type_confirmed_by_member_id = <Dr. Mehta's organization_member.id>,
       doc_type_confirmed_at = now()
 WHERE uploaded_by_member_id = app.current_member_id();
```

`document_confirmer_fk` only requires `(member_id, organization_id)` to exist, so any colleague's seat id is accepted. Two consequences: the record now claims a named clinician confirmed the classification, and `doc_type = 'other'` makes the file readable by **every receptionist in the hospital** via `030:1558` (`app.is_front_desk() AND doc_type IN ('scanned_document','other')`), with no care-team scope. `retracted_by_member_id` is forgeable the same way.

**Fix.** Extend `app.document_before_update()` to force `doc_type_confirmed_by_member_id`/`retracted_by_member_id` to `app.current_member_id()` and stamp the timestamps server-side (exactly the pattern `app.ai_finding_before_update()` uses at `030:1132-1147`), and refuse `doc_type_source = 'human'` from a non-staff caller.

### A4. A multi-role seat turns the patient column guard off. CONFIRMED. MEDIUM-HIGH.

`020:295-316`, `app.enforce_patient_writable_columns()`:

```sql
IF app.current_patient_id() IS NULL OR app.is_staff() THEN
  RETURN NEW;
END IF;
```

The README's own example seats exist: "a nurse treated at her own hospital is staff *and* a patient there" (`010:459-461`). For `roles = {patient, nurse}` or `{patient, receptionist}`, `app.is_staff()` is true, so the guard short-circuits — while `medication_order_update` (`020:1864-1869`) still admits her through the patient branch `patient_id = app.current_patient_id()` with `WITH CHECK (organization_id = app.current_org_id())`. `medication_order` carries **no** `enforce_append_only` trigger (`020:1583-1591` attaches only `t_touch`, `t_patient_columns`, `t_no_delete`).

```sql
-- seat = {receptionist, patient}, own chart
UPDATE public.medication_order
   SET drug_name = 'Alprazolam', dose_text = '2mg', frequency_text = 'BD',
       route = 'oral', status = 'active',
       prescriber_member_id = <any doctor's member id>
 WHERE patient_id = app.current_patient_id();
```

`medication_order_insert` correctly requires `app.has_role('doctor')`, but UPDATE lets her convert any existing row into a prescription of her choosing under a named prescriber. `medication_order_prescriber_fk` accepts any member in the org.

**Fix.** Change the short-circuit to `IF app.current_patient_id() IS NULL OR NOT app.is_patient() THEN` — or better, drop `is_staff()` and gate on `current_user IN ('service_role','postgres')` the way `030:855-858` does. Add `app.enforce_append_only('{status,ended_at,stop_reason,refill_requested_at,record_status,updated_at}')` to `medication_order`.

## PART B — Attacker holds a RECEPTIONIST login at Hospital A

### B1. Receptionist can re-point any patient's portal link — cross-patient disclosure. CONFIRMED. CRITICAL.

Same statement as A1 (`010:1406-1412`), reached through the `app.is_front_desk()` branch, which places **every** patient row in the tenant inside the `USING`, with `WITH CHECK` verifying only the tenant.

```sql
-- as receptionist@clinic.com
-- 1. free Priya's seat from her own chart (patient_portal_member_uk is a unique index)
UPDATE public.patient SET portal_member_id = NULL WHERE mrn = '108-921';

-- 2. aim that seat at a different patient's chart
UPDATE public.patient
   SET portal_member_id = '<Priya''s organization_member.id>'
 WHERE mrn = '104-882';          -- Rosa Delgado, St. Luke's
```

Both statements pass: `patient_portal_member_fk` only requires the seat to be in the same organisation, and `app.current_patient_id()` (`010:984-996`) simply joins `patient.portal_member_id → organization_member` and checks the seat is active and carries `'patient'`. Priya's seat does.

**Result:** the next time Priya signs in, `app.current_patient_id()` resolves to **Rosa's chart**. Priya then reads, through ordinary policies and with no further exploitation: Rosa's released `lab_result` rows, all `vital_sign`, `patient_condition`, `patient_allergy`, `encounter`, `medication_order`, `appointment`, `invoice`/`invoice_line`/`payment`, `patient_coverage`, patient-visible `ai_finding` rows, her own uploads and released `document` rows, and Rosa's `audit.event` history via `event_select` clause 3 (`040:1879`). Rosa is simultaneously locked out of her own portal. This is the objective — one patient reading another patient's records inside one hospital — reachable by the lowest-privilege staff role in the schema, in two `UPDATE`s that look like routine registration work.

Detection is weak: `040:1931` attaches the audit trigger as `audit.attach('public','patient', ARRAY['status','merged_into_patient_id'])`. **`portal_member_id` is not an alert column**, so the most identity-critical write on the table records `severity = 'normal'` and never surfaces in `audit.v_alerts`.

**Fix (three parts).**
1. Freeze `portal_member_id` in a BEFORE UPDATE trigger on `public.patient`; expose linking as `app.link_patient_portal(p_patient_id, p_member_id)` that verifies the seat's `app_user` matches the chart's identity and that the seat is not already linked.
2. Tighten `patient_update`'s `WITH CHECK` to repeat the `USING` predicate.
3. Add `portal_member_id` (and `mrn`) to the alert-column array at `040:1931`.

### B2. The column-limited view is trivially bypassable — but it is not what walls reception off. CONFIRMED, and the wall holds.

`public.v_front_desk_patient` (`020:1907-1922`) narrows columns, but `010:1443-1444` grants `SELECT ON public.patient` directly to `authenticated`, so `SELECT * FROM public.patient` works for a receptionist. The bypass yields nothing clinical — the view omits only `portal_member_id`, `created_by`, `created_at`, `updated_at`. So the view buys documentation value, not enforcement, and the README's framing ("the column list keeps a receptionist's query from mentioning a result", `020:1899-1901`) overstates it. RLS, not the view, is the control — and RLS holds: every clinical table's SELECT policy requires `app.is_clinician()` or the patient themselves, and `app.is_staff()` is correctly avoided on all of them.

**However, reception's actual reach contradicts the README's "No clinical rows at all" (README:279) in four places, all CONFIRMED and all deliberate-looking:**

| Surface | Statement | What reception learns about every patient, org-wide |
|---|---|---|
| `invoice_line_select` | `040:1806-1811` | `description` = "CT scan, chest", `service_code` 71260. 040:1805 calls this "diagnosis-shaped" itself. |
| `care_team_select` | `020:1698-1701` — gated on `app.is_staff()` | Who is on whose care team. Joined to tenant-readable `staff_profile.specialty` and `department`, this yields "patient X is under the oncology consultant". A clinical inference with no clinical row. |
| `document_select` | `030:1558` | Every document classified `scanned_document` **or `other`**, for every patient, with no care-team scope and no "you uploaded it" scope. `other` is the catch-all, and a clinician may reclassify a `lab_report` to `other` (only NULL and `radiology_image` are guarded at `030:871`), which silently publishes it to the whole front desk. |
| `appointment_select` | `020:1876-1880` | `chief_complaint`, org-wide. |

**Fix.** Either amend README:279 to state reception's real reach, or narrow it: drop `'other'` from `030:1558`, add a role predicate to `care_team_select` so reception sees only teams for patients with an appointment today, and consider whether `invoice_line.description` needs a coded/redacted projection for the Billing screen.

### B3. Receptionist write escalation beyond registration. CONFIRMED. MEDIUM.

From the same `patient_update` (`010:1406-1412`): a receptionist can set any patient's `status = 'merged'` (locking that patient out of the portal, since `app.current_patient_id()` excludes merged charts), rewrite any patient's `mrn` (colliding two charts' identifiers within the unique index's limits), and rewrite DOB/name/phone/email. Separately, `patient_coverage_update` (`040:1776-1779`) has `USING ... AND app.is_front_desk()` but `WITH CHECK (organization_id = app.current_org_id())`, so a receptionist can retarget a coverage row — including its `member_number` — to a different patient. Note 040 wrote `invoice_update` (`040:1793-1796`) correctly with `AND app.is_front_desk()` in the `WITH CHECK`; `patient_coverage_update` is the same author two statements later getting it wrong, which is why this reads as an oversight rather than a decision.

**Verdict on your item 3: reception cannot read clinical *results*.** `lab_result`, `lab_order`, `clinical_note`, `vital_sign`, `document_text`, and every `ai_*` table deny them. `v_lab_review_queue` is `security_invoker` and its inner joins to `lab_order`/`lab_panel` (both `is_clinician`/`is_staff`) collapse to zero rows. That part of the design works.

## PART C — Write escalation and the append-only claims (your items 4 and 6)

### C1. `app.allow_clinical_rewrite` is settable by the role it constrains. CONFIRMED. HIGH.

`020:277` inside `app.enforce_append_only()`, and identically `020:1470` inside `app.guard_clinical_note()`:

```sql
IF coalesce(current_setting('app.allow_clinical_rewrite', true), 'off') = 'on' THEN
  RETURN NEW;
END IF;
```

There is no privilege check. A dotted custom GUC in an unreserved class can be `SET` by any role. `authenticated` holds `UPDATE` on `lab_result`, `vital_sign` and `clinical_note` (`020:2177-2183`), and `lab_result_update` (`020:1825-1829`) admits any clinician on the care team — which any clinician can join in one `INSERT` (`020:1705-1714`).

```sql
-- as doctor@clinic.com, on the care team (or after one self-assert INSERT)
SET LOCAL app.allow_clinical_rewrite = 'on';

UPDATE public.lab_result
   SET value_numeric = 1.2, abnormal_flag = 'normal', reference_high = 2.2
 WHERE id = '<the lactate 3.1 that drove the sepsis flag>';
-- t_append_only returns NEW immediately; the reported value is rewritten in place,
-- with no supersedes_id, no record_status = 'amended', no second row.

UPDATE public.clinical_note SET body = 'Patient afebrile, no concerns.'
 WHERE id = '<a SIGNED note>';
-- app.guard_clinical_note() returns NEW at line 1471 before reaching the
-- "A signed note cannot be rewritten" branch at line 1475.
```

This directly falsifies README:199-201 ("Clinical rows are never deleted, and reported values are never edited... Enforced by `app.deny_hard_delete()` and `app.enforce_append_only()`") and `020:1322` ("The append-only trigger enforces that"). The audit trail does record the UPDATE (`040:1963`), so it is detectable — but the control described as an invariant is a caller-toggled preference.

**Fix.** Gate both hatches the way `030:854-858` already gates `scan_status`:

```sql
IF coalesce(current_setting('app.allow_clinical_rewrite', true), 'off') = 'on'
   AND (current_user IN ('service_role','postgres') OR current_user = session_user) THEN
  RETURN NEW;
END IF;
```

030 got this right; 010 and 020 did not. Apply the same to `app.deny_hard_delete()` (`010:195`).

### C2. Four clinical tables have no append-only guard at all. CONFIRMED. HIGH.

`enforce_append_only` is attached only to `vital_sign` (`020:1101`) and `lab_result` (`020:1384`); `clinical_note` has its own guard. **`medication_order`, `patient_allergy`, `patient_condition` and `encounter` carry only `t_touch` and `t_no_delete`.** So a clinician on the care team can, with no escape-hatch GUC and no amendment row:

```sql
UPDATE public.medication_order SET dose_text = '10g', route = 'intravenous'
 WHERE patient_id = '<a patient on my care team>';

UPDATE public.patient_allergy SET substance = 'none', severity = 'mild'
 WHERE patient_id = '<same>';
-- 020:541-543 promises "Never deleted — an allergy that turns out to be wrong is
-- inactivated with a reason, because 'we removed it' and 'it was never recorded'
-- must not look the same afterwards." An in-place rewrite makes them look the same.
```

Dose and allergy are the two most safety-critical values in 020. `patient_allergy`'s alert columns (`040:1952`) do include `substance`, so this alerts; `medication_order`'s (`040:1967`) are only `['status']`, so a dose rewrite records `severity = 'normal'`.

**Fix.** Attach `app.enforce_append_only(...)` to all four with explicit mutable-column lists, and add `dose_text`, `drug_name`, `route`, `frequency_text` to `medication_order`'s alert columns.

### C3. Sixteen UPDATE policies drop the role and per-patient predicate in `WITH CHECK`. CONFIRMED. HIGH (systemic).

Every one of these has a strong `USING` and `WITH CHECK (organization_id = app.current_org_id())`:

`010:1412` `patient_update` · `020:1720` `care_team_update` · `020:1743` `patient_condition_update` · `020:1759` `patient_allergy_update` · `020:1779` `encounter_update` · `020:1794` `vital_sign_update` · `020:1812` `lab_order_update` · `020:1829` `lab_result_update` · `020:1849` `clinical_note_update` · `020:1869` `medication_order_update` · `020:1890` `appointment_update` · `030:1601` `document_update` · `030:1657` `ai_finding_update` · `040:1762` `payer_update` · `040:1779` `patient_coverage_update`

In PostgreSQL, `USING` is evaluated against the OLD row and `WITH CHECK` against the NEW one. Tenant-only `WITH CHECK` therefore means: **anyone who can update one row can retarget it to any patient in the tenant.**

```sql
-- as a clinician on patient A's care team; no escape-hatch GUC needed
UPDATE public.clinical_note SET patient_id = '<patient B>' WHERE id = '<A''s signed note>';
-- app.guard_clinical_note() freezes body/note_type/occurred_at/signed_at/author_member_id
-- (020:1476-1480) but NOT patient_id. The note now sits in B's chart, authored by me,
-- and I can no longer read it back.

UPDATE public.encounter SET patient_id = '<patient B>' WHERE id = '<A''s encounter>';
-- succeeds when the encounter has no children (encounter_id_patient_uk children FK
-- is NO ACTION); fabricates an admission in a chart I have no relationship with.
```

`lab_result` and `vital_sign` are protected here only because `patient_id` is absent from their append-only mutable lists (`020:1385-1386`, `020:1102`) — i.e. by a different mechanism, accidentally. `appointment` is protected by `app.guard_appointment()` (`020:894-899`), which is the correct pattern and should be generalised.

**Fix.** Make every `WITH CHECK` repeat its `USING`. For the chart tables that is mechanical:

```sql
CREATE POLICY clinical_note_update ON public.clinical_note FOR UPDATE
  USING      (organization_id = app.current_org_id() AND app.is_clinician()
              AND patient_id = ANY (app.care_patient_ids()))
  WITH CHECK (organization_id = app.current_org_id() AND app.is_clinician()
              AND patient_id = ANY (app.care_patient_ids()));
```

Add a CI query alongside 020 §90.x asserting that no policy's `with_check` is a strict subset of its `qual`.

### C4. The break-glass accountability argument is defeated by `care_team_update`. CONFIRMED. HIGH.

`020:1716-1720`. `USING` admits `member_id = app.current_member_id()`; `WITH CHECK` verifies only the tenant.

```sql
-- as a clinician with any one open care_team_member row
UPDATE public.care_team_member
   SET member_id = '<a colleague''s member id>', patient_id = '<any patient>',
       role = 'attending', added_by = '<a third member''s id>'
 WHERE member_id = app.current_member_id();
```

Two things fall: (a) `care_team_insert`'s "clinician, **for themselves only**" restriction (`020:1711`) is bypassed on UPDATE, so one clinician can grant another chart access with no admin involved; (b) `added_by` is forgeable, which destroys the entire §26 argument (`020:556-565`, README:260-264) that self-assertion is acceptable *because* "it leaves a row with a name and a timestamp... an accountability control does not prevent, it makes the act undeniable." A forgeable name is not accountability. `040:1955` sets alert columns `['member_id','ended_at']` — `patient_id` and `added_by`, the two this exploit rewrites most usefully, are not among them.

Related, same table: `app.ensure_attending_on_care_team()` (`020:958-978`) is `SECURITY DEFINER` and inserts a `care_team_member` row for `NEW.attending_member_id`, bypassing `care_team_insert` entirely. `encounter_insert` (`020:1771-1774`) deliberately does not require care-team membership, and `encounter_attending_fk` accepts any member in the org — clinician or not. So one `INSERT INTO public.encounter (..., attending_member_id => <anyone>)` grants that member a care-team seat on any patient in the hospital. It does not escalate reception (all clinical policies require `app.is_clinician()`), but it does mean the "for themselves only" rule has a second bypass.

**Fix.** `WITH CHECK (organization_id = app.current_org_id() AND member_id = app.current_member_id() AND added_by = OLD.added_by)` — or, since ending an assignment is the only legitimate update, restrict the policy to that via a column guard freezing `patient_id`, `member_id`, `added_by`, `role`, `started_at`. Add `patient_id` and `added_by` to the alert columns. Constrain `ensure_attending_on_care_team()` to insert only when `NEW.attending_member_id = NEW.created_by`, or require the attending to hold a clinician role.

### C5. "Can anyone mark an AI finding accepted without authority?"

**Patient: no. Receptionist: no.** CONFIRMED. `ai_finding_update` (`030:1653-1656`) requires `app.is_clinician() AND patient_id = ANY (app.care_patient_ids())`, and `app.ai_finding_before_update()` (`030:1124-1134`) independently raises unless `app.is_clinician()`, refuses `pending` as a destination, and overwrites `reviewed_by_member_id`/`reviewed_at` with `app.current_member_id()` and `now()` rather than trusting the client. `chart_committed_at` gets the same treatment (`030:1136-1148`), and `ai_finding_chart_gate_ck` (`030:1020-1021`) is a CHECK, so it binds every writer. This is the best-guarded write path in the schema.

Two caveats, both CONFIRMED:

- **Any clinician, via break-glass.** Self-assert onto the care team (`020:1705-1714`), then accept and commit findings for any patient in the hospital. The §26 argument was made for *reading* a chart; it silently also confers AI-acceptance and chart-commitment authority, and C4 makes the resulting row's attribution forgeable.
- **`service_role` can forge a named doctor's acceptance.** `030:1104-1106`:

  ```sql
  DECLARE v_member uuid := app.current_member_id();
  BEGIN
    IF v_member IS NULL THEN
      RETURN NEW;      -- guard entirely off
    END IF;
  ```

  The model worker holds `UPDATE ON public.ai_finding` (`030:1747-1751`) and `BYPASSRLS`, and has no membership, so `v_member` is NULL and the guard returns immediately. It can set `review_state = 'accepted'`, `reviewed_by_member_id = <a real doctor's seat>`, `reviewed_at`, `chart_committed_at`, `chart_committed_by_member_id` in one statement; `ai_finding_review_pair_ck` only requires both to be non-null. **The component that generates the findings holds the privileges to rubber-stamp its own output under a named clinician's identity, and the resulting row is indistinguishable from a real review.** `030:940-943` sells this gate as unconditional; against the AI worker it is not. `actor_db_role` on the audit row would read `service_role`, which is the only tell.

  **Fix.** Split the worker's credentials: give the model worker `INSERT` only, and put `UPDATE ON public.ai_finding` behind a separate role. Or require `reviewed_by_member_id IS NOT NULL → actor is that member` in the guard rather than early-returning.

## PART D — The audit log (your item 5)

### D0. The append-only claim is real, not just commented. CONFIRMED positive.

I checked each of the four locks claimed at `040:1279-1285`, and the privileges were genuinely revoked:

- `040:1999-2000` — `REVOKE ALL ON audit.event FROM PUBLIC`
- `040:2015-2016` — `GRANT SELECT ON audit.event TO authenticated` followed by `REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON audit.event FROM authenticated`
- `040:2046-2047` — `GRANT SELECT, INSERT ON audit.event TO service_role` then `REVOKE UPDATE, DELETE, TRUNCATE ON audit.event FROM service_role` (this one matters most: `service_role` holds `BYPASSRLS`, and privileges are still checked for `BYPASSRLS` roles)
- `040:1292-1293` — `ENABLE` **and** `FORCE ROW LEVEL SECURITY`, with only `event_insert` (`FOR INSERT WITH CHECK (true)`) and `event_select` policies — no UPDATE or DELETE policy at all
- `040:1307-1309` — `audit.deny_mutation()` BEFORE UPDATE OR DELETE, and unlike `app.deny_hard_delete()` it has **no escape hatch**
- `040:2098-2104` — a self-check that fails the migration if a mutation policy is ever added

**Can the actor being audited UPDATE or DELETE their own events? No.** Four independent locks, each verified in the SQL. This is the strongest part of the schema.

### D1. The context columns are forgeable by the audited actor. CONFIRMED. MEDIUM.

`audit.set_request_context()` (`040:1076-1094`) is granted to `authenticated` (`040:2026`), and `audit.fn_row_audit()` copies its GUCs verbatim into the event (`040:1448-1455`).

```sql
SELECT audit.set_request_context(
  p_request_id  => gen_random_uuid(),
  p_client_ip   => '10.0.0.9'::inet,
  p_user_agent  => 'Prognosify/1.0',
  p_route       => '/patients',
  p_purpose     => 'treatment',
  p_acting_role => 'doctor');     -- as a patient seat
UPDATE public.patient SET phone = '...' WHERE id = app.current_patient_id();
-- the event records acting_role='doctor', purpose='treatment', a fabricated IP.
```

`audit.log_read()` is also granted (`040:2028`), so fabricated `read`/`export` events can be injected. The identity half is safe — `actor_app_user_id`, `actor_auth_uid`, `actor_org_id`, `actor_roles`, `actor_db_role` are all derived server-side, and `040:1536-1540` correctly notes `organization_id` is never taken from an argument. So the failure mode is attributable poisoning, not concealment. `040:1107-1111` frames `acting_role` as app-declared by design; the point worth making is that "app-declared" and "attacker-declared" are the same field once the app layer is bypassed.

**Fix.** Where the declared `acting_role` is not in `app.current_roles()`, record NULL rather than the claim, and flag the mismatch as `severity = 'alert'`.

### D2. THEORETICAL — RLS does not follow a partition accessed directly.

`audit.event` is `PARTITION BY RANGE (occurred_at)` (`040:1167`). Parent policies apply when the parent is queried; a partition queried by name is governed by its own `relrowsecurity` flag, which is never set. `audit.ensure_partitions()` does `REVOKE UPDATE, DELETE, TRUNCATE ON audit.<part> FROM PUBLIC` (`040:1225`) — but not `SELECT`, and the `audit.event_default` partition created at `040:1236-1242` gets no `REVOKE` at all. Today nothing grants `authenticated` anything on a partition, so `SELECT FROM audit.event_202608` fails on privilege. But the audit trail's tenant isolation currently rests on that single absence: one future `GRANT SELECT ON ALL TABLES IN SCHEMA audit`, or one `ALTER DEFAULT PRIVILEGES`, and every hospital's trail is readable with no RLS. Note `authenticated` already holds `USAGE ON SCHEMA audit` (`040:2003`).

**Fix.** `ALTER TABLE ... ENABLE/FORCE ROW LEVEL SECURITY` on each partition inside `ensure_partitions()` and on `event_default`, and add `REVOKE ALL ON audit.<part> FROM PUBLIC` there. Add a CI query asserting every `audit.event_*` partition has `relrowsecurity AND relforcerowsecurity`.

## PART E — Hard delete (your item 6)

**Verdict: no DELETE slips through today — but the guard named in the README is not what stops it.** CONFIRMED.

`authenticated` is granted `DELETE` on exactly two tables (`040:2012`): `public.org_setting` and `public.invoice_line`. Both are deliberate (`040:318-320`, `040:1817-1819`), both are audited via `audit.attach` (`040:1935`, `040:1940`), and `app.guard_invoice_line_immutable()` (`040:612-643`) refuses a delete once the invoice leaves `draft`. Everywhere else, `DELETE` fails on missing table privilege before any policy or trigger is consulted.

The weakness is that `app.deny_hard_delete()` — the mechanism README:199-201 credits — is caller-disableable:

```sql
-- 010:195
IF coalesce(current_setting('app.allow_hard_delete', true), 'off') = 'on' THEN
  RETURN OLD;
END IF;
```

`SET LOCAL app.allow_hard_delete = 'on'` requires no privilege. So the real control is the GRANT list, and it is one careless `GRANT DELETE` or one `FOR ALL` policy away from evaporating. Note that four `FOR ALL` policies already exist in the schema (`subscription_plan_write`, `feature_write`, `plan_feature_write`, `organization_entitlement_write`, `usage_metric_write`, `org_setting_write_*`, `invoice_line_write`) — `FOR ALL` includes DELETE, and the pattern is established. Same fix as C1: gate the hatch on `current_user`.

**What held up under attack, and deserves saying:** the `audit.event` append-only design (four real locks, actually revoked); vendor containment via `app.current_org_id()` returning NULL for a membership-less platform admin; `security_invoker` on all eight tenant-facing views, asserted at migration time; `app.sync_member_identity()` closing self-role-escalation; the `ai_finding` column guard against end users; the radiology-image ban as CHECK constraints; and the absence of `DELETE` grants.
