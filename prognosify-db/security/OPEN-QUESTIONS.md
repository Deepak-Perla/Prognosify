# Open design questions raised by the schema authors

> Generated by an adversarial review agent. No SQL was executed — findings are
> reasoned from the migration text. Treat CONFIRMED items as real defects.

1. The single-tenant drafts 001-004 must be REMOVED from the migration path before 010 runs. They create a conflicting public.patient, and their app.has_role(text) would sit alongside my app.has_role(app.org_role) as an overload — after which app.has_role('doctor') is ambiguous and every policy referencing it fails to resolve. This is the single most likely way to break the build.

2. Vendor tenant onboarding cannot be done from a super_admin web session: they can INSERT the first app_user/organization_member but cannot SELECT the row back (membership reads need an open support session), and PostgREST does INSERT ... RETURNING by default. Provisioning must run as service_role from a runbook. Confirm that is acceptable or ask me to add a provisioning RPC.

3. MRN allocation is left to the app. A per-tenant sequence would remove a front-desk race but needs a format decision from the owner (the UI shows '104-882').

4. The patient merge procedure — which chart survives, what happens to the loser's clinical rows — belongs to whoever owns the clinical tables (020). I modelled the state (status='merged' + merged_into_patient_id), not the operation.

5. Step-up authentication before a vendor opens a support session cannot be expressed in SQL; it needs a recent-MFA claim from an auth hook. Until then a stolen vendor session can open an operational (not clinical) session.

6. Access-token TTL is a Supabase project setting, not schema. The staleness argument assumes it is set to the shortest value the project allows.

7. patient.date_of_birth has CHECK (... <= current_date). PostgreSQL permits non-immutable functions in CHECK constraints, but if the team's policy forbids it, drop that half of the constraint.
