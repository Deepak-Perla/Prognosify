# Cross-tenant PHI read assessment — Prognosify multi-tenant schema

**Method note:** No PostgreSQL is available on this machine. Everything below is reasoned from the SQL text of `000/010/020/030/040`, `seed.sql`, `README.md`, `TESTING.md`. I could not execute a single query.

**Attacker model as I applied it:** a legitimate Hospital A `authenticated` session (doctor or `hospital_admin`), issuing arbitrary SQL as the `authenticated` DB role, with the application *business logic* bypassed. The decisive sub-question — whether that also lets the attacker rewrite their own JWT identity — is Finding 1 and I treat it explicitly.

---

## HEADLINE VERDICT

At the level of the RLS policies, helper functions, composite FKs and CHECK constraints, **tenant isolation is implemented correctly and I found no confirmed way for a Hospital A user (with a fixed Hospital A identity) to read Hospital B patient data.** The single-primitive design — every tenant policy opens with `organization_id = app.current_org_id()`, and that function resolves the org *only* from live `organization_member` rows for the authenticated subject — holds up under each attack I tried. The composite-FK house rule, the `security_invoker` discipline on every tenant-facing view, and the `search_path`-pinned SECURITY DEFINER helpers are all genuinely sound.

**The catastrophic failure is reachable through exactly one door, and it is not in the SQL policies — it is the identity seam (Finding 1).** If the attacker's connection can set `request.jwt.claims` / `request.jwt.claim.sub`, every policy in the database collapses, because all of them ultimately trust `app.current_auth_uid()`.

---

## FINDING 1 — The whole model rests on `app.current_auth_uid()`, and nothing in these files stops a raw `authenticated` session from rewriting it. (CONFIRMED conditional — CRITICAL)

**File / statements:** `010_tenancy_identity.sql:67-77` (`app.current_auth_uid`), `:96-111` (Supabase rebind to `auth.uid()`), and the fact that `current_org_id()` (`:887-909`), `is_super_admin()` (`:852-860`), `current_user_id()`, `care_patient_ids()` etc. all derive solely from it.

`app.current_auth_uid()` reads the GUC `request.jwt.claim.sub` / `request.jwt.claims` (or `auth.uid()`, which reads the same settings). `request.*` is an ordinary user-defined placeholder GUC. In stock PostgreSQL any role — including `authenticated` — may set such a placeholder with `set_config()`; nothing in these migrations reserves, revokes, or otherwise restricts it (there is no `ALTER ROLE ... SET`, no event trigger, no GUC hardening anywhere in the four files).

**Concrete SQL an attacker with a raw `authenticated` connection runs:**
```sql
select set_config('request.jwt.claims',
  json_build_object('sub','<any Hospital-B member auth_user_id>','role','authenticated')::text, true);
select set_config('request.jwt.claim.sub','<same uuid>', true);
select * from public.patient;          -- now returns Hospital B's charts
-- or impersonate a platform_admin's auth_user_id and read the vendor surface
```
**What it returns:** everything that identity can see. Impersonate a Hospital B clinician → that clinician's charts. Impersonate a `platform_admin` → `is_super_admin()` becomes true and the vendor-readable surface opens. This is total cross-tenant compromise.

**Why "conditional":** it depends on whether "application layer is bypassed" means (a) a direct DB connection as `authenticated` — then this is **fully exploitable and CONFIRMED**, or (b) requests still traverse PostgREST, which verifies the JWT signature and overwrites `sub` from the verified token — then `sub` is pinned to the real Hospital A identity and this door is shut. The schema's own docs assume (b) ("a browser can never forge it," `TESTING.md §0`). The task's phrasing ("issue arbitrary SQL … application layer is bypassed") points at (a).

**Severity:** Critical if reading (a) holds. It is the one place where the "single function is the whole boundary" design becomes the single point of failure.

**Fix:** This cannot be fixed inside these SQL files alone; it is a deployment control and must be stated as a hard prerequisite:
- Never expose the `authenticated` role on a directly reachable connection; all end-user traffic must pass through PostgREST (or an equivalent that verifies the JWT signature and sets `sub` from the verified payload only).
- Consider making the claim GUCs unforgeable at the role level where the platform allows it, and add a deployment test that proves an `authenticated` connection cannot alter `request.jwt.claim.sub`.
- Document this dependency in the README next to the `service_role`/`BYPASSRLS` warning — it is exactly as load-bearing and currently unstated.

## The nine hunt items, item by item

**1. A tenant table with RLS never enabled / no policy / `USING (true)` — NOT FOUND.**
Every table carrying `organization_id` has `ENABLE ROW LEVEL SECURITY` and at least one real policy; three independent CI gates enforce it (`app.v_tenant_rls_gaps`, the per-file "RLS enabled but no policy" check, `app.assert_no_vendor_phi_policies`). The one `USING/ WITH CHECK (true)` is `event_insert` on `audit.event` (`040:1864-1865`) — INSERT only, and no application role holds INSERT on that table (`040:2016`), so it is not a read path. `audit.event` is additionally `FORCE ROW LEVEL SECURITY`. No gap.

**2. A policy that filters by patient/care-team but forgets `organization_id` — NOT FOUND.**
Every clinical SELECT policy I read leads with `organization_id = app.current_org_id()` and only then applies `patient_id = ANY (app.care_patient_ids())` or `= app.current_patient_id()`. Both of those helpers are themselves org-scoped (`app.care_patient_ids()` filters `ct.organization_id = app.current_org_id()`, `020:237-246`; `app.current_patient_id()` filters `p.organization_id = app.current_org_id()`, `010:984-996`). The `EXISTS`-through-parent policies (`ai_risk_factor_select` `030:1675-1681`, `ai_citation_select` `030:1686-1696`, `invoice_line_select` `040:1806-1811`, `payment_select` `040:1822-1827`) also each carry their own `organization_id = app.current_org_id()` conjunct. There is no "by id, forgetting the tenant" policy.

**3. Views / materialized views without `security_invoker` — effectively NOT FOUND.**
Every view that touches tenant rows is `WITH (security_invoker = true)`: the five 020 read views, `app.v_effective_entitlement`, `030`'s `v_ai_uncited_findings`, and `040`'s `v_invoice_balance`, `v_tenant_health`, `audit.v_cross_tenant_access/v_alerts/v_read_coverage`. `020 §90.4` fails the migration if any 020 view loses the flag. The only three views without it — `app.v_tenant_rls_gaps`, `app.v_super_admin_policy_review`, `audit.v_unaudited_tenant_tables` — read `pg_catalog` only (table/policy names, never rows) and are not granted to `authenticated`. No leak.

**4. SECURITY DEFINER functions that leak (missing `search_path`, or returning rows the caller shouldn't see) — MOSTLY CLEAN; one minor metadata leak (Finding 2 below).**
Every SECURITY DEFINER function in all four files carries `SET search_path = pg_catalog, pg_temp` and fully-qualifies its object references, so temp-table shadowing does not apply. None returns another tenant's *rows* to a non-vendor. The argument-taking ones that are granted to `authenticated` return only booleans/scalars about commercial metadata (see Finding 2). `app.record_usage`, `app.refresh_organization_usage`, `app.seed_clinical_reference`, and the audit partition/retention helpers are granted to `service_role` only.

**5. SELECT covered but INSERT/UPDATE/DELETE not — can a Hospital A user INSERT with `organization_id = B`, or move a row across tenants? — NO.**
Every INSERT policy's `WITH CHECK` and every UPDATE policy's `WITH CHECK` pin `organization_id = app.current_org_id()` (= A for the attacker), so a B-tenant value is rejected. Cross-tenant *inserts* are further blocked by the composite FKs (a `(parent_id, organization_id)` reference to a B parent under org A does not exist). Cross-tenant *moves* are blocked by the same `WITH CHECK` plus explicit freeze triggers: `app.sync_member_identity` (`010:530-536`), `app.guard_appointment` (`020:894-899`), `app.document_before_update` (`030:838-849`). Tables with no write policy for `authenticated` (`ai_analysis_run`, `ai_risk_score`, `document_text`, `platform_admin`, `organization_usage_daily`) fail closed. No cross-tenant write path.

**6. Helper functions spoofable via a client-influenceable JWT claim — CHECKED, correctly contained (except Finding 1).**
`app.jwt_org_id()` (`010:81-93`) and `app.requested_org_id()` (`010:865-873`) *do* read a client-influenceable claim (`app_metadata.organization_id` / top-level `organization_id`). This is the obvious attack. But it is only a **hint**: `app.current_org_id()` (`010:887-909`) intersects it against the `live` CTE — memberships the caller actually holds in a `trial/active` org. Spoofing the claim to Hospital B yields `(SELECT organization_id FROM live WHERE organization_id = B)` = empty → NULL → every tenant policy denies. I confirmed a single-hospital attacker cannot make `current_org_id()` return B. This is a correctly-built defense, not a hole. (It becomes moot only under Finding 1, where the attacker changes `sub` itself rather than the org hint.)

**7. FK-based inference via constraint-violation error messages — CONTAINED (theoretical only).**
The composite-FK house rule defeats the classic oracle: an attempt to reference a Hospital B row while `organization_id = A` fails as `(B_id, A) does not exist`, which does not confirm B's row exists. MRN uniqueness is per-tenant (`patient_mrn_uk`, `010:687-688`), deliberately so, so a duplicate-MRN insert only collides within org A. A few **global** unique indexes exist — `patient_portal_member_uk` (`010:689-690`), `document_storage_key_uk` (`030:331-332`), `vital_sign_supersedes_uk` (`020:1070`), `lab_result_supersedes_uk` (`020:1270`), `clinical_note_supersedes_uk` (`020:1434`) — and in principle a unique-violation vs FK-violation message could be an existence oracle. In practice each is gated so the attacker cannot even form the colliding insert: `document.storage_key` must pass `document_storage_key_tenant_ck` (prefix `org/A/…`, `030:299-300`), so a B-prefixed key is rejected before any uniqueness check; the `supersedes_id`/`portal_member_id` columns are constrained by composite FKs to same-org parents, and all require guessing UUIDs. I rate this theoretical, not confirmed.

**8. Storage-key convention — derivable, but not a read path in the DB (theoretical, depends on out-of-DB controls).**
`app.storage_prefix(uuid)` is `IMMUTABLE` and granted to `authenticated` (`010:208-212`, `:1456`), so a Hospital A user can compute `app.storage_prefix('<B uuid>') = 'org/<B>/'` and knows the documented layout `org/<org>/patient/<patient>/…`. That is convention knowledge, not access: the bucket policy is a prefix match on the caller's own org and the DB does not sign URLs. The real exposure lives entirely outside these files — whatever signs download URLs must enforce both `document.scan_status='clean'` and that the key prefix matches the caller's org (`README` "Object storage keys", `030 §grants` NOTICE). Flag: the tenant-first key is the *only* thing separating tenants in object storage; if the bucket policy or URL signer is misconfigured, this becomes a real cross-tenant leak that these files cannot prevent. Put an explicit test in the API suite.

**9. super_admin containment & cross-tenant auditing — containment holds; auditing has a documented read-side gap.**
A non-vendor cannot reach a super_admin path: `platform_admin` has **no INSERT/UPDATE policy** (`010:1384-1387`) and `authenticated` holds only SELECT on it, gated behind `is_super_admin()` — so the attacker can neither read it nor mint themselves into it. `app.open_support_session` requires an existing `platform_admin` row (`010:1154-1158`); `approve_support_session` is scoped to the caller's own org (`010:1191-1197`). Containment is structural.
The auditing caveat is real and worth stating: **cross-tenant *reads* are not audited unless the application voluntarily calls `app.log_chart_open()` / `audit.log_read()`** — PostgreSQL has no SELECT trigger (`040 §5.1`). So `audit.v_cross_tenant_access` catches cross-tenant *writes* but a cross-tenant *read* (including the Finding 1 scenario, or any future read hole) would leave no trace. This is honestly documented, not hidden, but it means "cross-tenant access is genuinely audited" is true only for writes.

## FINDING 2 — Cross-tenant commercial-metadata disclosure via feature helpers (CONFIRMED, LOW; no PHI)

**File / statements:** `app.org_has_feature(uuid, text)` `010:1054-1068`, granted to `authenticated` `010:1454-1455`; `app.org_feature_limit(uuid, text)` `040:816-830`, granted `040:2024`. Both are SECURITY DEFINER and take an **arbitrary** `organization_id`.

**Concrete SQL:**
```sql
select app.org_has_feature('<Hospital B uuid>','billing');      -- true/false
select app.org_feature_limit('<Hospital B uuid>','staff_seats'); -- e.g. 250
```
**Returns:** Hospital B's plan/entitlement flags and seat limits. This is commercial metadata (which plan a competitor hospital is on, roughly how large it is), **not patient data**. It is a cross-tenant boundary crossing, so worth recording, but it is not the catastrophic failure.

**Severity:** Low.

**Fix:** If the org-scoped variants must stay callable by `authenticated`, gate them to `p_organization_id = app.current_org_id() OR app.is_super_admin()`, or move the arbitrary-org overloads to `service_role` and have the caller-facing wrappers (`app.has_feature(text)`, `app.feature_limit(text)`) use `current_org_id()` implicitly — which they already do; the arbitrary-org DEFINER variants simply do not need to be in the `authenticated` grant list.

## NOTED (in-scope-adjacent, not cross-tenant)

- **Intra-tenant chart reach via self-assignment.** `care_team_insert` (`020:1705-1714`) lets any Hospital A clinician add *themselves* to any Hospital A patient's care team, immediately opening that chart. This is the deliberate break-glass path (`020 §26`, `TESTING §5`) and is strictly **within** Hospital A — it is not a cross-tenant leak, but it means "care-team scoping" is an accountability control (leaves an audited row), not a hard barrier, against a malicious insider in the same hospital. Out of scope for the stated objective; flagging so it isn't mistaken for a second barrier.
- **Client-controlled audit context.** `audit.set_request_context()` (`040:1076-1094`) is granted to `authenticated`, so a client can set `audit.acting_role`, `audit.purpose`, `client_ip`, etc. to false values. `audit.log_read` correctly takes `organization_id` from `current_org_id()` not from arguments (`040:1529`), so an attacker can spam/mislabel audit rows but cannot attribute a read to another tenant. Integrity-of-trail concern, not a read hole.

---

## Bottom line for the objective

Under a Hospital A identity that the attacker cannot change, I could not construct a working cross-tenant patient-data read: the policies, helper functions, composite FKs and CHECKs are consistent and mutually reinforcing, and the obvious JWT-org-hint attack is correctly neutralized by validating the hint against real membership. **The one path to reading another hospital's patient data is Finding 1 — rewriting the authenticated subject.** Whether that path is open is not decided by any of these SQL files; it is decided by whether the deployment lets an `authenticated` connection set `request.jwt.claim.sub`. That question should be answered and tested before this schema is trusted with real charts, because if the answer is "yes," the entire, otherwise-solid isolation model is bypassed in two `set_config` calls.
